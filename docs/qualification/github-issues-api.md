# GitHub Issues read-only API research

Research for [Research GitHub Issues API, auth reuse and rate limits for read-only Issue access](https://github.com/ManuelUsoz/spence/issues/261). GitHub.com documentation accessed 2026-11-22; provider limits and APIs may change.

## API shapes

- REST `GET /repos/{owner}/{repo}/issues` lists repository issues and supports state (`open`, `closed`, `all`), assignee, milestone, labels, `since`, sort and direction. `GET /repos/{owner}/{repo}/issues/{issue_number}` fetches one. Both can return pull requests: test for the `pull_request` property. A PR's `id` here is its issue ID, not its pull-request ID. REST issue data includes number, URL, title, body, state/state reason, labels, assignees, milestone, comment count and timestamps. The default body is raw Markdown. [Issues endpoints](https://docs.github.com/en/rest/issues/issues)
- Repository issue comments have a separate paginated endpoint, `GET /repos/{owner}/{repo}/issues/{issue_number}/comments`; issue objects contain a count, not full comment bodies. [Issue comments](https://docs.github.com/en/rest/issues/comments)
- `GET /search/issues?q=repo:OWNER/REPO+is:issue+...` supports text and GitHub search qualifiers and avoids PR results with `is:issue`. Search exposes at most 1,000 results per query and can report `incomplete_results` on timeout. Search sees only resources accessible to the token. [Search endpoint](https://docs.github.com/en/rest/search/search#search-issues-and-pull-requests), [issue search syntax](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests)
- GraphQL `Repository.issues` returns an issue connection, `Repository.issue(number:)` fetches an Issue, and `issueOrPullRequest(number:)` is an `IssueOrPullRequest` union. The `Issue` type exposes fields including body, state, labels, assignees, milestone, comments and timeline; nested connections require pagination. [Repository schema](https://docs.github.com/en/graphql/reference/repos), [Issue schema](https://docs.github.com/en/graphql/reference/issues)
- GraphQL `Issue.closedByPullRequestsReferences` returns PRs that may close the issue, with options including closed PRs and manually linked PRs. `timelineItems` exposes cross-reference and connected events; `CrossReferencedEvent.source` may be an Issue or PullRequest and `willCloseTarget` indicates a closing reference. A cross-reference is not necessarily a closing link, and a closing-reference connection is not a list of every mention. REST timeline cross-reference events likewise identify PR sources by `source.issue.pull_request`. [Issue schema](https://docs.github.com/en/graphql/reference/issues), [REST event types](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types), [timeline endpoint](https://docs.github.com/en/rest/issues/timeline)

## Authentication and permissions

- The sibling [Git hosts spec](../specs/git-hosts-and-pull-requests.md) specifies, rather than establishes as implemented, `HostAuth` Device Flow, PAT and `gh auth token` import; its verification matrix requires classic token `repo` and `read:org`. GitHub documents OAuth `repo` as broad public/private repository access including issues; `read:org` is organization membership/team read access, not the issue-specific permission. Scopes cannot exceed the user's own access and users may grant less than requested. [OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps), [OAuth vs GitHub App permissions](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)
- For fine-grained PATs and GitHub App tokens, repository issue listing and issue detail require repository **Issues: read**. Comment and timeline endpoints accept either **Issues: read** or **Pull requests: read**. Public resources can be read without authentication. Fine-grained token repository selection and the user's actual access still limit visibility; an imported token cannot be assumed to carry the sibling spec's classic scopes. [Issues endpoints](https://docs.github.com/en/rest/issues/issues), [comments](https://docs.github.com/en/rest/issues/comments), [timeline](https://docs.github.com/en/rest/issues/timeline)
- The search endpoint documents no fine-grained permission requirement, but repository/resource visibility still applies. A GitHub App user token query that combines issue and PR types returns an empty result; specify `is:issue` or `is:pull-request`. [Search endpoint](https://docs.github.com/en/rest/search/search#search-issues-and-pull-requests)

## Limits, pagination and caching

- REST's primary authenticated user limit is normally 5,000 requests/hour, shared by requests made on the user's behalf; unauthenticated requests normally have 60/hour per IP. Search is a separate rate-limit resource: ordinary authenticated search normally allows 30 requests/minute and unauthenticated 10/minute. Secondary limits also apply. `x-ratelimit-*` headers expose the resource, remaining budget and reset; rate limiting may return 403 or 429. Follow `Retry-After` if present, otherwise reset when remaining is zero; for secondary limits without either, wait at least a minute and use increasing delays. [REST limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [search limits](https://docs.github.com/en/rest/search/search#rate-limit), [troubleshooting](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api)
- Most REST endpoints supply `ETag` and/or `Last-Modified` validators. An authorized conditional request returning `304 Not Modified` does not count against the primary limit; this does not promise exemption from secondary limits. Issue detail documents 304. [REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api), [issue detail](https://docs.github.com/en/rest/issues/issues#get-an-issue)
- REST uses `Link` headers for pagination; issue list and comments default to 30, maximum 100 per page. GraphQL uses cursors and `pageInfo`; connections require `first` or `last` in the range 1–100. GraphQL has a separate point-based primary limit and query/node limits. [REST pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api), [GraphQL pagination](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api), [GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)

## Disabled issues and missing resources

- Repository metadata exposes REST `has_issues` and GraphQL `hasIssuesEnabled`. GitHub documents 410 for **creating** an issue when repository issues are disabled; do not generalize that particular endpoint's status to every read. Issue detail documents 301 for a transferred issue, 404 for inaccessible transferred/deleted issues, and 410 for deleted issues in a readable repository. A 404 can also hide an inaccessible private resource. [Repository REST endpoint](https://docs.github.com/en/rest/repos/repos#get-a-repository), [GraphQL repository](https://docs.github.com/en/graphql/reference/repos), [issue endpoints](https://docs.github.com/en/rest/issues/issues), [REST troubleshooting](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#404-not-found-for-an-existing-resource)
