# Azure DevOps Boards: read-only integration research

Research for [Research Azure DevOps Boards work items API, auth and URL shapes](https://github.com/ManuelUsoz/spence/issues/262). Sources accessed 2026-11-22. Facts only; this does not select a design.

## Organization and project discovery

- Azure DevOps Services uses `https://dev.azure.com/{organization}/{project}/_git/{repository}`; Microsoft also documents project-less clone URLs such as `https://dev.azure.com/{organization}/_git/{repository}`. Thus a remote does not always identify the project. The older `{organization}.visualstudio.com` service domain remains supported. [Clone docs](https://learn.microsoft.com/en-us/azure/devops/repos/git/clone?view=azure-devops), [Git auth examples](https://learn.microsoft.com/en-us/azure/devops/repos/git/auth-overview?view=azure-devops).
- Modern SSH clone form is `git@ssh.dev.azure.com:v3/{organization}/{project}/{repository}`. Microsoft says old SSH URLs use `vs-ssh.visualstudio.com` and continue working, but the cited current documentation does not specify all legacy path variants. SSH config can replace the actual hostname with an alias, making the remote alone insufficient to establish the service. [SSH documentation](https://learn.microsoft.com/en-us/azure/devops/repos/git/use-ssh-keys-to-authenticate?view=azure-devops).
- Organization/project derived from a remote describes its Azure Repos host, not proof that this is the intended Boards project. Work item API project arguments accept name or ID. [Get work item](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/get-work-item?view=azure-devops-rest-7.1).

## Authentication and authorization

- Microsoft recommends Microsoft Entra tokens over PATs. Delegated OAuth acts within the signed-in user's Azure DevOps permissions; Entra Conditional Access and MFA apply. Azure DevOps OAuth is deprecated and new registrations stopped in April 2025. Its `vso.work` scope documented on REST operations covers reading work items, queries, boards and metadata and executing/searching queries; it is an Azure DevOps OAuth scope, not an Entra scope. [Entra overview](https://learn.microsoft.com/en-us/azure/devops/integrate/get-started/authentication/entra?view=azure-devops), [WIQL security](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/wiql/query-by-wiql?view=azure-devops-rest-7.1).
- Azure DevOps' Entra resource is `499b84ac-1321-427f-aa17-267ca6975798`; Microsoft documents requesting `499b84ac-1321-427f-aa17-267ca6975798/.default` and presenting the token as Bearer. PATs use HTTP Basic with any username and the PAT as password; PAT work-item read permissions must be granted and organizational policies can restrict PATs. [Token API authentication](https://learn.microsoft.com/en-us/rest/api/azure/devops/tokens/?view=azure-devops-rest-7.0), [PAT documentation](https://learn.microsoft.com/en-us/azure/devops/organizations/accounts/use-personal-access-tokens-to-authenticate?view=azure-devops), [states API](https://learn.microsoft.com/en-us/rest/api/azure/devops/processdefinitions/states/list?view=azure-devops-rest-4.1).
- Device code flow is for public clients; the user visits a sign-in page and enters a code, and the client receives tokens. Conditional Access can block the flow; Microsoft recommends blocking it where possible. [Desktop device flow](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-desktop-acquire-token-device-code-flow), [Conditional Access](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-authentication-flows).
- Azure CLI can obtain an Entra access token for that resource with `az account get-access-token --resource 499b84ac-1321-427f-aa17-267ca6975798` after `az login`, using the correct tenant context. Microsoft describes it for ad hoc requests; this does not establish a durable imported credential or automatic renewal. [Azure CLI guidance](https://learn.microsoft.com/en-us/azure/devops/cli/entra-tokens?view=azure-devops).

## Read APIs and limits

- `POST /{org}/{project}/{team}/_apis/wit/wiql?api-version=7.1` executes a WIQL query, with optional `$top`; results include work item references rather than hydrated fields. `GET /{org}/{project}/_apis/wit/workitems/{id}?api-version=7.1` fetches one. Batch POST `/.../_apis/wit/workitemsbatch?api-version=7.1` takes IDs, field selection, expansion and error policy, with a maximum of 200 IDs; the list GET also requires IDs and has a 200-item maximum. [WIQL](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/wiql/query-by-wiql?view=azure-devops-rest-7.1), [get](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/get-work-item?view=azure-devops-rest-7.1), [batch](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/get-work-items-batch?view=azure-devops-rest-7.1), [list](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/list?view=azure-devops-rest-7.1).
- Azure DevOps Services documents 30-second query execution, 20,000 results and 32,000 characters as limits; results at the limit can be truncated without an error. The WIQL endpoint documents `$top`, but no continuation token or offset. [Limits](https://learn.microsoft.com/en-us/azure/devops/organizations/settings/work/object-limits?view=azure-devops), [WIQL](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/wiql/query-by-wiql?view=azure-devops-rest-7.1).
- Comments have a separate paged `GET /{org}/{project}/_apis/wit/workItems/{id}/comments`, accepting `$top` and `continuationToken`; its documented version is `7.1-preview.4`. [Comments](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/comments/get-comments?view=azure-devops-rest-7.1).
- Work-item expansion can include relations. Microsoft's example represents a PR link as `ArtifactLink` with a `vstfs:///Git/PullRequestId/...` URI, not a normal browser URL. PR APIs also list work items linked to a PR; links to PRs and commits are distinct. [Batch expansion](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/get-work-items-batch?view=azure-devops-rest-7.1), [PR artifact example](https://learn.microsoft.com/en-us/previous-versions/azure/devops/integrate/previous-apis/git/pull-requests/work-items?view=tfs-2017), [PR links](https://learn.microsoft.com/en-us/azure/devops/repos/git/pull-requests?view=azure-devops).
- Microsoft tracks consumption in TSTUs, with a 200 TSTU sliding five-minute user limit. Clients may see delay, blocking, `Retry-After` in seconds, and `X-RateLimit-*` headers including remaining, reset and cost; resource header values can change and should not drive computations. [Rate limits](https://learn.microsoft.com/en-us/azure/devops/user-guide/service-limits?view=azure-devops).
- The cited work-item, WIQL and batch endpoint references do not document conditional GET / `ETag` / `If-None-Match` support. No guarantee of 304-based caching for these endpoints was established by this research; an endpoint-specific live verification would be needed. Work item responses expose `rev`, but that alone is not evidence of conditional HTTP support. [Get work item](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/get-work-item?view=azure-devops-rest-7.1).

## Types, states, and client libraries

- Work item types and states depend on process and can be customized. The process state API exposes a `stateCategory` alongside each state; documented categories include Proposed, In Progress, Resolved, Completed and Removed. A display state name alone cannot safely indicate completion across processes. The API returns type-specific state definitions; a mapping from category to application status is a design decision, not an Azure-defined universal open/closed boolean. [State categories](https://learn.microsoft.com/en-us/azure/devops/boards/work-items/workflow-and-state-categories), [process states](https://learn.microsoft.com/en-us/rest/api/azure/devops/processes/states/list?view=azure-devops-rest-7.1).
- Microsoft's `azure-devops-node-api` package offers WorkItemTracking and WorkItemTrackingProcess clients and PAT connection examples. Plain HTTP can call the documented REST endpoints directly; API version is explicit in those endpoints. [Node client](https://github.com/microsoft/azure-devops-node-api), [REST API versioning](https://learn.microsoft.com/en-us/azure/devops/integrate/concepts/rest-api-versioning?view=azure-devops).
