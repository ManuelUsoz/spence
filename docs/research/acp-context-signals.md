# ACP context signals and summary handoff

Research for [#57](https://github.com/ManuelUsoz/spence/issues/57), under [#55](https://github.com/ManuelUsoz/spence/issues/55). Checked 2026-11-13. Planning evidence only; no estimation UX or summary policy is selected here.

## Conclusions

- SDK **2.6.0 already has stable ACP v1 context utilization and compaction lifecycle/summary types**. No SDK upgrade or v2 migration is required merely to represent them. Availability in a schema does not mean every Agent emits them.
- Current Claude and Codex adapters emit `usage_update`; both support manual `/compact` and automatic compaction lifecycle. Claude can expose a displayable compaction summary; current Codex deliberately cannot.
- Google Antigravity has a documented **native `agy acp` server**. It must not be replaced with Gemini CLI. Its published ACP documentation does not establish the context utilization/compaction wire fields needed here; mark those capabilities unverified pending a pinned-binary probe.
- ACP has no generic tool-free “summarize without changing context” RPC, no generic Clear RPC, and no cross-provider import of private Agent history. Ordinary text prompts can carry a Spence summary, but producing one is an Agent turn with no protocol guarantee against tool use.

## Versions and evidence boundaries

Spence pins `@agentclientprotocol/sdk` to 2.6.0. The package root exports stable v1; `/unstable` and `/experimental/v2` are separate entry points. Inspected local installed declarations against the [SDK v2.6.0 generated schema](https://github.com/agentclientprotocol/typescript-sdk/blob/8649e0af14cd1112bf02e5f137217f8c3fcf7e90/src/v1/schema/types.gen.ts) and [package exports](https://github.com/agentclientprotocol/typescript-sdk/blob/8649e0af14cd1112bf02e5f137217f8c3fcf7e90/package.json).

Adapter snapshots are Claude **0.106.0**, commit [`4804917`](https://github.com/agentclientprotocol/claude-agent-acp/tree/4804917a6fa7050490d1d62c6689e78c231c752a), and Codex **2.6.0**, commit [`6567651`](https://github.com/agentclientprotocol/codex-acp/tree/656765115f82253c79f87918abb77189c114a799). These are current source snapshots, not assertions about an installed global executable. Adapter and ACP SDK version numbers are independent. The old Zed Codex implementation is archived and [redirects new installs to the App Server adapter](https://github.com/zed-industries/codex-acp). No paid/live model sessions were run.

## Protocol meanings and operations

In SDK 2.6.0 stable v1, `UsageUpdate.used` means tokens currently in context, `size` the context-window capacity, and optional `cost` cumulative session cost. These are separate measurements. `compaction_update` addresses one entity by `compactionId`, with `in_progress`, `completed`, `failed`, `cancelled`, or future string status. `summary` is optional displayable content, with patch semantics: omission preserves, null/empty array clears. `compaction_summary_chunk` appends content. Clients must advertise `clientCapabilities.session.compaction: {}` before receiving this contract. A completed compaction may have no summary. See the [pinned stable schema](https://github.com/agentclientprotocol/typescript-sdk/blob/8649e0af14cd1112bf02e5f137217f8c3fcf7e90/src/v1/schema/types.gen.ts).

The separate unstable `PromptResponse.usage` describes input/output/cache/reasoning totals, with generated comments referring both to prompt-turn usage and totals across turns. Do not reinterpret this as occupancy or assume identical counter scope across adapters; inspect each mapping. [Pinned unstable schema](https://github.com/agentclientprotocol/typescript-sdk/blob/8649e0af14cd1112bf02e5f137217f8c3fcf7e90/src/v1/unstable/schema/types.gen.ts).

There is no stable generic `session/compact`, `session/clear`, or `session/summarize` method. Slash commands are Agent-defined and discovered through available-command updates, then sent as prompt text. A generic client must not assume every command exists. `session/new` creates private Agent context; `session/load` is capability gated and refers to that Agent's existing session, not arbitrary Spence transcript import. See [stable methods](https://github.com/agentclientprotocol/typescript-sdk/blob/8649e0af14cd1112bf02e5f137217f8c3fcf7e90/src/v1/stable/acp.ts), [slash commands](https://agentclientprotocol.com/protocol/v1/slash-commands), and [session setup](https://agentclientprotocol.com/protocol/v1/session-setup).

## Claude

The adapter's occupancy is itself a **proxy derived from the latest top-level model response**: uncached input + cache-read input + cache-write input + output. These are the latest response's figures, not the cumulative sum of repeated context across model calls. It excludes subagent messages from the main context snapshot and avoids zero-usage synthetic command banners wiping a valid measurement. During compaction it uses the boundary's `post_tokens`; older SDK frames without this field temporarily report zero until corrected. This zero is not proof of an empty context. [Usage arithmetic](https://github.com/agentclientprotocol/claude-agent-acp/blob/4804917a6fa7050490d1d62c6689e78c231c752a/src/session-usage.ts), [v1 event mapping](https://github.com/agentclientprotocol/claude-agent-acp/blob/4804917a6fa7050490d1d62c6689e78c231c752a/src/v1/acp-agent.ts).

Capacity starts from a backend/model cache, otherwise an identity-text heuristic or 200,000 default; background `getContextUsage().rawMaxTokens` and result `modelUsage` refine it. The code explicitly documents that raw and result capacities can differ. Backend routing, credentials and extended-context entitlement matter. A reported capacity therefore may initially be an adapter guess; ACP's bare `used`/`size` fields do not express that distinction. Model switching refreshes capacity, but does not justify declaring context empty. [Capacity implementation](https://github.com/agentclientprotocol/claude-agent-acp/blob/4804917a6fa7050490d1d62c6689e78c231c752a/src/context-window.ts).

Current compaction code handles start, terminal outcomes, streaming summaries and PostCompact-hook summaries. It removes private analysis and model-facing continuation framing before exposing displayable text; unrecognized framing may yield no summary. Replay reconstructs completed compactions from persisted compact-summary messages, potentially with a different ID from the live event. Clients lacking the capability get legacy synthetic tool calls instead. This supersedes older reports that Claude always discards summaries. [Lifecycle and summary extraction](https://github.com/agentclientprotocol/claude-agent-acp/blob/4804917a6fa7050490d1d62c6689e78c231c752a/src/context-compaction.ts).

`/compact` can invoke the existing compaction flow; it changes the outgoing Agent's context and is not a neutral export operation. `/clear` is explicitly filtered from exposed SDK slash commands. The internal clear coordinator restarts private context for a plan workflow; its existence does not establish a supported user Clear command. [Command filtering](https://github.com/agentclientprotocol/claude-agent-acp/blob/4804917a6fa7050490d1d62c6689e78c231c752a/src/slash-commands.ts), [internal reset](https://github.com/agentclientprotocol/claude-agent-acp/blob/4804917a6fa7050490d1d62c6689e78c231c752a/src/clear-context-coordinator.ts).

## Codex

The current adapter maps App Server `thread/tokenUsage/updated`: `last.totalTokens` becomes ACP `used`, and `modelContextWindow` becomes `size`. It retains `total` separately for cumulative usage and suppresses the utilization update if capacity is missing/nonpositive. Cached input is a breakdown of counted usage, not a number to subtract from occupancy. Native subagent usage belongs to that subagent's context. This is a last-inference utilization reading, not a continuously exact serialization of private context. [Mapping](https://github.com/agentclientprotocol/codex-acp/blob/656765115f82253c79f87918abb77189c114a799/src/CodexEventHandler.ts), [usage shapes](https://github.com/agentclientprotocol/codex-acp/blob/656765115f82253c79f87918abb77189c114a799/src/app-server/v2/ThreadTokenUsage.ts).

`/compact` is advertised and handled as a Codex turn command, not ordinary free-form model instructions. Both auto and manual compaction yield ID-addressed lifecycle events for opted-in clients; failures/cancellation close unfinished entries, while later turn failure does not undo successful compaction. Replay preserves completed persisted entries but cannot replay failures Codex never persisted. **No displayable summary is exposed**: the adapter intentionally omits it rather than extracting encrypted/internal replacement history. No Clear command is established by the inspected advertised command list. [Commands](https://github.com/agentclientprotocol/codex-acp/blob/656765115f82253c79f87918abb77189c114a799/src/CodexCommands.ts), [adapter compaction contract](https://github.com/agentclientprotocol/codex-acp/blob/656765115f82253c79f87918abb77189c114a799/docs/session-compaction.md).

Official OpenAI documentation confirms App Server usage notifications and manual compaction with a `contextCompaction` item lifecycle. These underlying APIs are evidence about Codex; Spence's ACP integration should consume the adapter translation rather than bypass it. [Official OpenAI App Server documentation](https://learn.chatgpt.com/docs/app-server).

## Google Antigravity

Google documents `agy acp` over stdio, with session loading/resuming/listing/closing, cancellation, slash commands and model/thinking selection. Third-party models are restricted to named IDE clients; availability to Spence is unverified. This is native Antigravity ACP, not Gemini CLI or an unofficial bridge. Public docs do not establish `usage_update`, compaction notification/summary schemas, a supported ACP Compact/Clear operation, or version-specific wire guarantees. No authoritative public adapter implementation was identified in this investigation. [Native ACP documentation](https://antigravity.google/docs/ide/extensions/acp/).

Its CLI `/context` panel documents model capacity, categorized usage and checkpoint summaries; automatic compaction exists. That panel separately accounts checkpoint buffers, so its percentage cannot automatically be equated with an ACP occupancy ratio. CLI `/clear` resets active context, but a TUI command does not prove ACP availability. Confirm command discovery and captured notifications against a pinned `agy` version before promising these operations. [Context documentation](https://antigravity.google/docs/cli/commands/context), [CLI reference](https://antigravity.google/docs/cli/reference/). Native ACP is permitted by the user's updated direction; protocol details still belong behind Spence's domain translation boundary.

## Observable estimates and blind spots

Spence can observe the prompts it sends (including attachment bytes/text and resource links), streamed Agent text/thoughts, published tool-call arguments/results, model/config changes, reported utilization and compaction boundaries/summaries. Existing main code already translates compaction entities and advertises support, but drops `usage_update` in transcript mapping. Spence supplies neither filesystem nor terminal client capabilities; Agent-local work need not be fully visible. [Baseline dispatcher](https://github.com/ManuelUsoz/spence/blob/e21be55/electron/acp/acpClientDispatcher.ts), [mapper](https://github.com/ManuelUsoz/spence/blob/e21be55/electron/acp/acpMappers.ts), [capabilities](https://github.com/ManuelUsoz/spence/blob/e21be55/electron/acp/acpSessionManager.ts).

Consequently, counting visible transcript tokens is a heuristic, not a complete context ledger. Hidden system instructions, tool definitions, workspace rules, internally read files, truncation, private reasoning, subagents, resource expansion, images/audio tokenization and provider-specific retention are missing or differently represented. Repeated cumulative input counts double-count reused history. Byte/character counts are not model tokens; changing models changes tokenization and effective capacity. These are deductions from the boundary and mappings above, not measured error bounds.

After compaction, old visible transcript remains historical; summing it again overstates retained context. A reported post-compaction reading can anchor an estimate, while a summary alone does not reveal hidden retained items. After clear/new private context, baseline overhead still exists. After Agent switching, destination capacity/tokenization and injected summary define a new measurement boundary; source occupancy cannot be transferred. Last reading, model/provider identity, source, timestamp and reset boundary are useful provenance inputs, without selecting their UX here.

## Summary generation and transfer

A destination can receive a textual handoff through ordinary `session/prompt` content after `session/new`, with its chosen Agent/Model. That starts a model turn; ACP has no generic passive seed-only request. Agent-private IDs, encrypted compaction data, tool state, permissions and caches are not portable. Native same-provider fork APIs are unnecessary for the agreed Spence fork: a new Session in the same Project with summary and chosen Agent/Model. These are protocol deductions from [prompt turns](https://agentclientprotocol.com/protocol/v1/prompt-turn) and the session setup contract above.

Requesting an outgoing summary through a normal prompt is possible, but instructions such as “summarize only; do not use tools” are not a protocol enforcement mechanism. ACP does not guarantee no reads/writes/commands or no extra context change; permission rejection cannot undo already auto-authorized or Agent-local work. Claude's compact summary is an available artifact with side effects and possible omission; Codex's is absent; Antigravity export is unverified. A Spence-generated summary over its own transcript avoids asking the live Agent to act, but lacks hidden Agent context. Which source, fallback, review and tool restrictions to use remains a decision.

Only stopped Turns may enter switch/fork workflows, as already agreed. Producing a summary itself may create additional work to cancel/fail. No implementation should treat “source turn stopped” as proof that summary production or destination startup cannot fail.

## Questions this evidence leaves for decisions

1. Is a reported adapter proxy sufficient as “reported,” retaining its caveats separately from Spence estimates, especially guessed Claude capacity and legacy zero after compaction?
2. When an Agent cannot export a neutral summary, should handoff use a dedicated outgoing summary turn, a transcript-based summary, user-edited text, or a defined fallback order?
3. Must destination seeding wait for a separate acknowledgement turn, or may summary and next user instruction share one prompt? What happens if startup succeeds but generation fails?
4. Should Clear always replace private Agent context while preserving Spence Transcript, rather than depend on inconsistent provider slash commands?
5. What minimum pinned Antigravity probe is required before enabling reported usage, lifecycle, Compact and Clear independently? Absence of evidence for one must not disable its established native ACP integration.

Validation: source and schema inspection only. No application code changed, no model behavior/estimation accuracy claimed, and no live credentialed adapter compatibility test performed.
