# Markdown rendering under Spence’s CSP

Research for [Research Markdown rendering and sanitization under Spence’s CSP](https://github.com/ManuelUsoz/spence/issues/134), 2026-11-16. Recommendation only; the architecture and subset remain a human decision in [Decide the Markdown rendering architecture and supported subset](https://github.com/ManuelUsoz/spence/issues/136).

## Local baseline

`src/app/features/session/thread.ts` joins text parts, appends `MessageDelta.text` to its matching message, and uses a regular-expression `textRuns()` split into prose, inline code and fenced blocks. It discards the fence info string and does not implement nested Markdown. Extending the *rendering seam* is viable; extending that regex into a CommonMark parser is not recommended. `package.json` has no Markdown parser or highlighter dependency.

`src/index.html` permits only self scripts (no inline scripts or eval); styles allow inline styles, and images allow self/data/blob, not arbitrary remote HTTPS images. `electron/main.ts` denies new windows and sends only HTTPS new-window URLs to `shell.openExternal`. Its navigation guard uses prefix comparison (including a broad file:// production prefix), not exact URL/origin validation. Do not assume a plain same-window anchor is safely routed. These are local-code findings, not claims that Markdown support already exists.

## Comparison matrix

All parser rows support headings, emphasis, ordered/unordered lists, links, blockquotes, fenced code with an info string, and images as syntax. Syntax support does not authorize loading image URLs. CommonMark defines these constructs; GFM adds tables/task lists. [CommonMark](https://spec.commonmark.org/0.31.2/).

| Approach | Tables / task lists | Raw and inline HTML | Streaming / rendering | Integration cost and security |
| --- | --- | --- | --- | --- |
| Existing textRuns regex extended by hand | Neither today; custom work for every construct | Currently text interpolation, not HTML execution | Re-splits accumulated text; no stable syntax tree | Small baseline, high correctness cost for nesting, escapes, reference links and malformed input |
| remark-parse + remark-gfm → mdast → Angular templates | Both via remark-gfm | HTML nodes can be explicitly omitted or shown as literal text; never compile them | Parse accumulated source, reconcile typed nodes; stable DOM requires deliberate identities | Most control over code controls, image components, semantic markup and link events; maintain exhaustive node renderer and URL policy |
| marked → DOMPurify → Angular innerHTML | GFM option supports both | Parser emits HTML; sanitize final result with restrictive allowlist | Whole-input parse and sanitize per update; binding can replace descendant DOM | Short pipeline, but Angular components/directives are not instantiated from injected markup; controls need wrappers/delegated events |
| markdown-it → DOMPurify → Angular innerHTML | Tables default; task lists need a plugin | html option defaults false; enabling HTML still requires sanitizer | Token parsing is available; default render produces whole HTML string | Good configurable rules; plugin maintenance adds review surface; its tokens could also feed Angular templates |
| micromark (+ GFM extension) → DOMPurify → Angular innerHTML | Both with GFM extension | Dangerous HTML/protocol options default off; do not enable casually | Has a streaming interface, but document references require buffering; not a stable incremental UI DOM API | Low-level compiler; use mdast tooling/remark when a tree is wanted rather than treating HTML compiler output as an AST |

Evidence: [remark](https://github.com/remarkjs/remark), [remark-gfm](https://github.com/remarkjs/remark-gfm), [marked options and extensions](https://marked.js.org/using_advanced), [marked security warning](https://marked.js.org/), [markdown-it defaults and API](https://github.com/markdown-it/markdown-it), [micromark API and buffering caveats](https://github.com/micromark/micromark). Parser choice and renderer choice are independent: marked tokens and markdown-it tokens can also be rendered structurally.

## Streamed text

None of the ordinary parse/render calls promises stable Angular nodes or append-only HTML across MessageDelta events. Inference from CommonMark: a later underline can turn a paragraph into a heading; later reference definitions can resolve earlier links; closing fences and emphasis delimiters change interpretation. Never parse and concatenate each delta independently. A supposedly finished block can still contain unresolved reference links. [CommonMark parsing strategy](https://spec.commonmark.org/0.31.2/#appendix-a-parsing-strategy), [micromark buffering discussion](https://github.com/micromark/micromark#streaming).

Recommended experiment: retain canonical accumulated text, coalesce visual updates, parse the active message as a whole, cache settled message results, and perform a final full parse when the Turn settles. Preserve selection, scroll position and code-copy state through reconciliation. Do not equate a parser’s streaming I/O interface with an incremental rendering algorithm. Long messages need profiling and possibly a renderer worker; no heavy parsing/highlighting belongs in Electron main. No benchmark or measured latency claim is made here. Settle-only rendering avoids repeated work but delays rich formatting; the human decision must choose that UX explicitly.

## HTML, links and security

Structured rendering should use static Angular templates and text/property bindings, with a closed node allowlist. Never compile Agent output as Angular templates. HTML-node omission differs from literal escaping: dropping `<b>` tags may preserve adjacent Markdown text, while an HTML block node can contain the entire block. Choose and test the exact behavior, including inline and block cases. [Angular security](https://angular.dev/best-practices/security).

For HTML output, sanitize after parsing and highlighting, immediately before binding. Restrict tags/attributes to the supported subset, exclude scripts, event attributes, styles, frames, forms, SVG/MathML and arbitrary IDs unless explicitly required. DOMPurify’s defaults cover more than this product needs; use an HTML profile/allowlist. Do not mutate sanitized HTML afterward with unsanitized content. Keep Angular’s normal HTML sanitization; do not use bypassSecurityTrustHtml as a shortcut. DOMPurify and Angular can remove different attributes, so test the final DOM, including disabled task inputs and code classes. CSP is defense in depth, not a sanitizer. [DOMPurify configuration and foot-guns](https://github.com/cure53/DOMPurify), [Angular security](https://angular.dev/best-practices/security).

Both approaches must validate destinations independently of parser escaping. Recommend HTTPS-only external links initially, matching the existing main handler; reject javascript:, data:, file:, custom protocols and credentials-bearing destinations. Relative and fragment links need an explicit product policy rather than accidental app navigation. A structured anchor can emit an intent; an HTML host can delegate clicks using closest anchor and intercept default navigation. New-window target=_blank HTTPS anchors can reuse the existing setWindowOpenHandler, provided attributes survive sanitization and all activation paths are tested. A future RPC route, if chosen, must go through DesktopApi and revalidate in main; features must never call Electron directly. Include keyboard activation, middle/modifier clicks and context-menu/new-window behavior in the prototype. Main navigation validation deserves an exact URL/origin check when this integration is specified; its current prefix guard is insufficient as the sole boundary. [Electron navigation and openExternal guidance](https://www.electronjs.org/docs/latest/tutorial/security).

Markdown image syntax is not an ImagePart and must not automatically fetch arbitrary URLs. Remote images are blocked by today’s CSP; allowing them would change both privacy and security policy. Data/blob URLs also need size/type and provenance constraints, rather than accepting all parser output. This overlaps the existing image-delta decision, not a newly uncovered separate ticket.

## Fence language and highlighting footprint

A fence info string is an author-supplied hint, not language detection. CommonMark convention uses its first word as a language. Preserve the raw code for copy, normalize supported aliases against a fixed grammar registry, and fall back to plain text for absent/unknown hints. Never interpolate the info string into unchecked HTML attributes. [CommonMark fenced blocks](https://spec.commonmark.org/0.31.2/#fenced-code-blocks).

No parser above bundles syntax highlighting as an inherent requirement. Default recommendation: plain fenced code plus language label/copy; defer highlighting until its value is demonstrated. highlight.js supports explicit language and heuristic highlightAuto; limit imported grammars and avoid auto-detect work on every delta. Its output is HTML, so it still needs a safe final rendering path. [highlight.js API](https://highlightjs.readthedocs.io/en/latest/api.html).

Shiki provides bundled versus fine-grained imports; full language/theme bundles add substantial optional code. Its engine choice matters under CSP (Oniguruma/WASM versus JavaScript engine), so verify the selected engine against the shipped Electron CSP before adopting; do not relax script-src to make it work. Standard highlighting output may introduce inline color styles; map tokens to existing theme variables/classes to meet Spence’s no-hard-coded-colors rule. No compressed byte figures are asserted: exact footprint depends on pinned version, engine, grammars, themes and build tree-shaking and must be measured. [Shiki bundles](https://shiki.style/guide/bundles), [engines](https://shiki.style/guide/regex-engines).

## Recommended default and remaining decisions

Recommend remark-parse + remark-gfm to a small typed Angular renderer, omitting raw HTML nodes, preserving source text, using plain fences initially and coalesced active-message reparsing. This trades renderer implementation work for explicit URL/image policy, existing component affordances and predictable typography. Sanitized innerHTML remains credible if the team values a smaller initial renderer and accepts delegated controls and DOM replacement behavior. This is an informed recommendation, not an architecture selection.

Use font-sans for prose, font-mono for code at normal weight; do not turn dynamic thread headings into font-display. Render task lists as noninteractive status. Keep parsing code renderer-local unless a demonstrated shared consumer justifies moving it; presentational ui wrappers must not acquire Effect or domain services. No glossary/ADR change is justified by a research recommendation.

The existing architecture/subset decision owns raw HTML semantics, destinations, streaming, subset and language/copy policy. The existing chat renderer prototype owns focus/selection stability, large-message performance, adversarial markup, keyboard links and final sanitized DOM checks. The existing image-delta decision owns inline image provenance and loading policy. These sharpen existing questions, so no duplicate ticket is needed. Clear only the Markdown architecture/subset/streaming fog already represented by those tickets; leave image and Skill fog unchanged. This branch contains research only, must never be merged, and has no PR. No runtime code changed; no application test run is claimed.
